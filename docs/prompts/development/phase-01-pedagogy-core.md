# Phase 01 开发 Prompt 与复盘

本文档从项目实施第一天开始增量记录。它既保存可以复用的 Vibe Coding Prompt，
也记录 AI 的假设、实际执行证据和纠偏过程。阶段结束时在此基础上完成最终复盘，
不依赖事后回忆。

## 使用原则

1. 一个 Prompt 只解决一个明确阶段：分析、测试、实现或验证。
2. 先规定允许修改的文件和禁止事项，再描述目标。
3. 要求 AI 给出可运行的验收命令，不能只说“确认可用”。
4. 新功能遵循红灯、绿灯、重构；没有看到正确失败，不进入实现。
5. 每轮记录原始 Prompt、AI 假设、执行结果和偏离计划的原因。

## 可复用 Prompt 模式

### 模式 1：只读设计

适用于还没有决定数据结构、模块边界或实现方案时。

```text
你正在为 [项目/用户群体] 设计 [功能]。

先阅读：
- [需求或项目简介]
- [相关现有代码]
- [现有架构或迁移规范]

本轮只分析，不修改文件。
请输出：
1. 目标和非目标
2. 建议的数据结构、字段、约束和关系
3. 模块职责与依赖方向
4. 需要测试的正常、边界和失败场景
5. 你作出的假设，以及需要我确认的事项

不要生成尚未确认的实现代码。
```

### 模式 2：TDD 红灯

适用于已经确认设计，准备实现一个最小行为时。

```text
实现计划中的任务 [编号和名称]。

当前只执行红灯阶段：
1. 只修改 [测试文件]
2. 编写描述 [目标行为] 的最小测试
3. 不创建或修改生产实现
4. 运行 [精确测试命令]
5. 确认测试被正常收集，并因 [缺失行为] 而失败

如果是测试收集错误、拼写错误或环境错误，先修正测试，
直到它成为能够证明需求尚未实现的有效失败。
报告失败测试数量和关键错误，不要进入绿灯阶段。
```

### 模式 3：TDD 绿灯

红灯已经被验证后使用。

```text
红灯已经因 [缺失行为] 正确失败。

现在执行绿灯阶段：
1. 只修改 [允许的生产文件]
2. 编写让现有失败测试通过的最小实现
3. 不添加测试没有要求的功能
4. 运行目标测试和全部回归测试
5. 运行 [Lint/类型检查/构建命令]

如果失败，先判断是实现、测试还是计划问题；
不能通过删除断言或放宽需求来让测试变绿。
```

### 模式 4：完成前验证

适用于提交和推送之前。

```text
在宣称任务完成前，重新运行：
- [目标测试]
- [全部测试]
- [Lint/类型检查/构建]
- git diff --check
- git status --short --branch

阅读完整输出并报告测试总数、失败数和检查结果。
只有所有验收条件都有新鲜证据时才提交。
提交信息必须包含任务编号；推送后比较本地 HEAD 与远程分支哈希。
```

### 模式 5：实现复盘

适用于每 2 至 3 个任务后的学习检查点。

```text
回顾刚完成的任务 [范围]，不要继续写代码。
请用初学者可以复述的语言说明：
1. 我们解决了什么用户或工程问题
2. 为什么使用当前模块边界
3. 红灯具体证明了什么
4. AI 最初的假设中，哪些被接受、修改或拒绝
5. 哪些命令构成完成证据
6. 下一任务依赖本轮的什么结果

最后给我 2 至 3 个检查理解的问题，并把摘要写入项目复盘文档。
```

## 本阶段实际执行记录

### 任务 1：最小 Python 工程

使用的核心 Prompt：

```text
先只写描述包可导入这一期望行为的测试，不写包实现。
运行测试并确认它因 backend.app 缺失而失败。
然后只创建 pyproject.toml 和最小包标记，安装项目，
重跑目标测试、全部测试、Ruff 和 git diff --check。
验证通过后单独提交并推送功能分支。
```

执行结果：两条导入测试先因 `ModuleNotFoundError` 失败，创建最小包结构后通过。
Pytest 和 Ruff 被安装在项目专用 `.venv`，没有污染系统 Python。

### 任务 2：教学领域类型

使用的核心 Prompt：

```text
先用测试定义 Difficulty、HintLevel 的 1 至 5 范围，
以及 StudentState 修改时必须失败的不可变约束。
看到有效红灯后，只实现两个枚举和冻结数据类，不加入算法。
```

第一次运行在测试收集阶段因顶层导入失败。这虽然指向缺失模块，但测试函数没有执行，
证据质量不足。测试被调整为在函数内导入，第二次运行正常收集两条测试，并产生两个预期失败。
最小实现完成后，本阶段累计四条测试通过。

### 任务 3：独立提示等级计算

使用的核心 Prompt：

```text
只执行提示等级算法的红灯阶段。
覆盖新问题的难度差公式、首次提示最高为 4、同一问题逐级加一，
以及编程和数学难度不同情况下的独立结果。
测试必须被正常收集，并且只因 compute_hint_levels 尚不存在而失败。

红灯确认后，仅在 pedagogy.py 实现满足这些测试的纯函数；
不读取数据库、环境变量或模型输出，不添加元数据校验或能力更新功能。
```

执行结果：新增七个测试实例全部因 `pedagogy` 模块缺失而正确失败。
最小算法完成后，九条教学测试和十一条全量测试通过。原计划只用相同难度同时测试
两个维度，执行时增加了“编程难、数学易”的案例，直接证明两个维度不会互相复用结果。

### 任务 4：有效能力 EMA 更新

使用的核心 Prompt：

```text
只执行能力更新的一个红绿循环。
先测试两个可手工复算的数值案例，以及当前能力超出 1 至 5 时的输出边界。
测试必须在原有提示等级案例继续通过的同时，因 update_effective_level 缺失而失败。

红灯确认后，实现提示加权的 EMA：先规范化输入，再计算 demonstrated_level、
learning_rate 和 updated，最后限制输出范围。不要同时更新 StudentState，
不要加入数据库写入或模型判断。
```

执行结果：原有九条教学测试继续通过，四个新增案例因目标函数缺失而失败。
实现后十三条教学测试通过；其中 `2.0 -> 2.24` 和 `5.0 -> 4.808` 两个结果可由公式独立复算。

### 任务 5：结构化教学元数据校验

使用的核心 Prompt：

```text
为 LLM 分类结果建立应用边界，但本轮不调用模型。
先测试合法值的 1 至 5 限制、首条消息的保守降级、缺少字段、
非布尔标记、非整数难度，以及 Python 中 bool 属于 int 的特殊情况。

红灯确认后，只增加不可变 PedagogyMetadata 和 coerce_pedagogy_metadata。
验证顺序必须是：必填字段、精确类型、历史一致性、数值范围。
非法结构抛出 ValueError；可安全修正的范围和历史冲突采用确定性降级。
```

执行结果：五个初始案例在原有十三条教学测试继续通过时正确失败，最小实现后转绿。
质量复查发现原计划的字符串布尔案例同时缺少其他字段，无法证明精确类型校验；因此补齐完整输入，
并增加 `True` 作为难度的案例。临时削弱生产校验后，这两个案例均失败；恢复实现后重新转绿。

### 任务 6：模块化产品 Prompt Builder

使用的核心 Prompt：

```text
对照正式规格实现 Prompt Builder，不调用任何真实模型。
红灯必须覆盖：角色目标、永久原则、学生状态、独立提示等级、全部上下文字段、
允许/禁止行为、注入边界、信息不足、学生可见输出、版本记录、字段类型和长度限制。

用户消息必须被转义并包裹为不可信数据，不能通过伪造结束标签逃出边界。
沟通风格只能使用应用批准的固定值。Prompt Builder 只消费已经计算好的 StudentState，
不能重新计算难度、提示等级或能力值。

任何评测结果都必须来自真实执行；规格中的示例版本号和“7/7 通过”不能直接冒充本项目结果。
```

执行结果：第一轮五条测试因 Builder 缺失而失败，实现后转绿。审查时发现沟通风格可以向受信任区
注入任意文字，并且示例评测记录会构成虚假声明；新增两项红灯后，加入风格白名单，版本改为
`pedagogy-v0.1.0`，相关评测标记为计划中且 `not run`。最终六条 Prompt 测试通过。

### 任务 7：Provider 合同与 Mock Provider

使用的核心 Prompt：

```text
先定义模型调用边界，不接入任何真实厂商 SDK。
红灯测试必须证明：相同请求产生完全相同的响应；响应包含内容、Provider、模型和 Token 估算；
空输入也能在没有网络、API Key 或环境变量的情况下返回合法结果。

红灯确认后，只实现不可变 TutorRequest、TutorResponse、TutorProvider Protocol，
以及确定性的 MockTutorProvider。不要让 Provider 计算提示等级、拼装产品 Prompt 或写数据库。
```

执行结果：两条测试因 Mock Provider 模块缺失而失败。最小实现后转绿；Provider 合同只依赖
项目内部数据类型，没有引入厂商 SDK、网络调用或密钥配置。

### 任务 8：确定性命令行 Tutor

使用的核心 Prompt：

```text
把现有教学模块串成最小可运行 CLI，不在入口文件复制业务规则。
先写两个独立进程端到端测试：合法输入必须输出可解析 JSON，并包含独立提示等级、Provider、
模型、内容和 Token；越界难度必须返回退出码 2、清晰错误信息且不输出成功载荷。

红灯确认后，CLI 只负责参数解析和编排：StudentState -> compute_hint_levels ->
build_system_prompt -> TutorRequest -> MockTutorProvider -> JSON。不要接入数据库、网络或真实模型。
```

执行结果：两个测试都因 CLI 模块缺失而失败；实现后转绿。真实命令行示例返回编程提示等级 3、
数学提示等级 1、Provider `mock`、模型 `deterministic-tutor-v1`，并给出非零 Token 估算。

### 任务 9：教学、Prompt 与运行文档

使用的核心 Prompt：

```text
从当前分支已经验证的代码和测试生成面向学习者的文档，不凭实施计划猜测功能。
教学文档必须给出实际函数、公式、数值案例、失败边界和尚未验证的教育假设。
Prompt 文档必须解释全部模块、上下文转义与截断、Provider 边界、版本真实性和应用层防护。

更新 README 的当前状态、限制、目录导航和可直接执行的虚拟环境命令。
先运行全套测试、Ruff 和真实 CLI，获得证据后才能写“已完成”；文档完成后重新执行相同命令，
并检查 Markdown 结构、差异格式和敏感信息。
```

执行结果：新增教学框架和产品 Prompt 设计文档，README 从“尚未开始实现”更新为当前真实状态；
第二次学习检查点的原始回答和校正已保存。没有发生架构变化，因此本任务不新增流程图。

### 任务 10：阶段验收与远程同步

使用的核心 Prompt：

```text
先让学习者用自己的话回答五项验收问题，不替学习者生成答案：
提示等级的后端控制、编程与数学独立、Prompt Builder 与 Provider 分工、
Mock Provider 的测试价值，以及首次提示最高为 4 的原因。

记录原始回答、仍不准确之处和校正。然后重新运行全套测试、Ruff、真实 CLI、
git diff --check、敏感信息扫描和远程哈希比较。只有全部证据通过，才能把 Phase 01 标记为完成。
最后使用分支收尾流程，让学习者选择合并、创建 PR、保留或丢弃。
```

执行结果：学习者完成五项口头验收。31 条自动测试、Ruff 和真实 CLI 在阶段收尾前通过；
最终文档修改后再次运行同一套门禁。分支集成由学习者在收尾选项中决定。

## AI 提出的假设

| 假设 | 处理 | 原因 |
| --- | --- | --- |
| Python 3.11+ 可用 | 接受 | 本机实测为 Python 3.12.0 |
| 缺少 Pytest 可以算 TDD 红灯 | 拒绝 | 这只能证明环境没准备好，不能证明需求测试有效 |
| 可以直接在 `main` 实现和推送 | 拒绝 | 产品代码使用隔离 worktree 和功能分支 |
| 顶层导入失败足以作为任务 2 红灯 | 修改 | 调整为测试被收集后在函数内产生预期失败 |
| 返回两个提示值即可证明独立计算 | 拒绝 | 新增两个维度输入不同且输出不同的行为测试 |
| 任意 `ValueError` 都足以证明错误类型被校验 | 拒绝 | 测试数据必须先通过其他边界，确保失败来自目标规则 |
| 规格中的 Prompt 版本和评测结果可以原样复制 | 拒绝 | 版本属于当前实现，未执行的评测必须明确标记为 `not run` |
| 沟通风格字符串可以直接进入受信任 Prompt | 拒绝 | 当前只接受应用批准的固定风格，防止规则注入 |

## 出现的错误

| 阶段 | 现象 | 根因 | 处理 |
| --- | --- | --- | --- |
| 首次推送 | Git 无法读取 GitHub 用户名 | Git 未接入已授权的 GitHub CLI 凭据 | 配置 Git 使用 GitHub CLI 凭据助手并重新验证 |
| 工具安装 | 首次输出在 Ruff 下载处提前结束 | 安装过程输出与完成状态不同步 | 分别查询 Pytest 和 Ruff 版本，以实际安装结果为准 |
| 任务 2 红灯 | Pytest 收集阶段中断 | 被测模块在文件顶层导入 | 将导入移入测试函数，确保测试被收集后失败 |
| 执行检查 | 偶发 `Resource temporarily unavailable` | 桌面应用父进程下积累大量未回收子进程 | 将验证拆成单进程命令并记录环境限制；项目文件未受影响 |

## 本阶段学到的原则

- Prompt 不是越长越好，而是边界、顺序和验收标准必须明确。
- “运行失败”不等于“有效红灯”；失败原因必须正好对应尚未实现的需求。
- 领域类型只定义系统在谈论什么，算法负责决定系统如何变化。
- Git 提交和测试输出共同构成可追溯的开发记录。

## 学习检查点

### 检查点 1：任务 3 至 5

学习者回答摘要：

1. 首次提示需要保留学生思考空间，遵守“教学而非直接给答案”的原则。
2. 编程和数学是两个独立评估维度，需要分别分析。
3. 学生能力需要在已有状态上通过 EMA 迭代更新。

校正与补充：首次最高等级 4 仍允许局部例子，完整答案等级 5 留给多轮求助；学生能力值是状态，
EMA 是确定性更新算法，并非两个并列参数。不能由 LLM 直接修改状态的根本原因，是模型输出具有
随机性且属于不可信输入，能力更新必须可测试、可复算和可审计。

### 检查点 2：任务 6 至 8

学习者回答摘要：

1. 开发 Prompt 与底层代码、前后端和架构施工有关；产品 Prompt 面向 AI Tutor 的实际行为。
2. Prompt Builder 负责完整教学规则、双提示等级、上下文隔离、注入防护、长度限制和版本记录；
   对 Tutor Provider 的职责暂时不清楚。
3. 暂时不能解释为什么第一版使用 Mock Provider。

校正与补充：开发 Prompt 是给构建产品的 AI 编程代理的施工合同，不局限于底层代码；产品 Prompt
是运行时模型的行为合同。Tutor Provider 是模型适配器，接收统一 `TutorRequest` 并返回统一
`TutorResponse`，隔离厂商 SDK、网络、密钥和 Token 细节。先用 Mock 可以让核心流程离线、免费、
确定且可重复，避免把网络、额度、密钥或模型随机性误判为业务代码错误。

### Phase 01 最终学习验收

1. **为什么提示等级不能完全交给 LLM？**
   学习者指出 LLM 不能提供强约束，规则必须通过后端实施。补充：Prompt 可以引导模型，
   但后端确定性算法才提供可测试、可复算和不可被用户消息覆盖的等级边界。
2. **为什么编程和数学要独立计算？**
   两者是独立评估维度；学生能力和题目难度可能分别高低，合并会掩盖真实困难。
3. **Prompt Builder 与 Tutor Provider 分别负责什么？**
   Prompt Builder 把教学规则、状态和不可信上下文组合为系统 Prompt；Provider 选择并调用具体
   模型实现，再把厂商结果统一为 `TutorResponse`。
4. **Mock Provider 如何让测试不依赖付费 API？**
   它不需要密钥、费用或网络，相同输入产生相同输出，使失败更容易定位，并允许先验证完整流程。
5. **第一次回答为什么最高只能从等级 4 开始？**
   首次回答需要保留学生思考和整合空间，贯彻 `Teach, don't solve`；完整答案等级 5 留给多轮求助。

验收结论：学习者已经能够解释本阶段的核心边界。Provider 的完整职责和后端强约束是在追问后
掌握的内容，已保留原始回答与校正，后续接入真实模型时需要再次复习。
